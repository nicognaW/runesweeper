## Q1. How does JSMinesweeper decide each move? (trivial deductions, local analysis, probability engine, dead tiles, 50/50s, brute force, guess selection)

### Takeaway
JSMinesweeper runs a fixed pipeline in `doSolve()`. (1) Single-cell trivial rules. (2) An exact BigInt probability engine over "boxes" (tiles that share the same set of witnesses). It merges witnesses one at a time like dynamic programming, compresses states on the frontier, convolves the independent edges by mine count, and weights each total mine count by `C(minesLeft − m, tilesOffEdge)`. (3) Dead-tile detection and 2-tile, extended and 2x2 50/50 and pseudo-50/50 detection, which force an early guess. (4) An exact game-tree search (BFDA) once fewer than 1000 solutions remain. (5) Otherwise a one-ply look-ahead "secondary safety" score over candidates within 0.1 of the safest living tile, plus several dominance tie-breaks.

### Cited Findings

**Top-level pipeline (`solver_main.js`, `doSolve`)**, in order, and each step returns as soon as it produces moves:
- It scans every tile. Revealed tiles with covered, non-mine neighbours become `witnesses`. Their covered neighbours become `witnessed` (the "edge", marked `onEdge`). It counts `minesLeft = num_bombs − known mines` and `squaresLeft` (covered tiles) — [JS solver_main.js `doSolve`](https://github.com/DavidNHill/JSMinesweeper/blob/c30bd65ba7de859889ea76dccc1d227bed6e51d3/Minesweeper/client/solver_main.js)
- If `minesLeft == 0` every covered tile is cleared. If `minesLeft == squaresLeft` every covered tile is a mine — [JS solver_main.js](https://github.com/DavidNHill/JSMinesweeper/blob/c30bd65ba7de859889ea76dccc1d227bed6e51d3/Minesweeper/client/solver_main.js)
- **Trivial analysis** (`trivial_actions`), per witness: if found mines == value, every other covered neighbour is clear. If value == flags + covered, every covered neighbour is a mine. If any trivial move exists the solver returns at once without running the probability engine. It skips this step only in `fullProbability` or efficiency modes — [JS solver_main.js `trivial_actions`](https://github.com/DavidNHill/JSMinesweeper/blob/c30bd65ba7de859889ea76dccc1d227bed6e51d3/Minesweeper/client/solver_main.js); README: "If plays are discovered then processing ends at this stage" — [JSMinesweeper README](https://github.com/DavidNHill/JSMinesweeper/blob/c30bd65ba7de859889ea76dccc1d227bed6e51d3/README.md)
- Next it constructs and runs a `ProbabilityEngine`. If `finalSolutionCount == 0` the board is invalid. If every tile is dead or a mine (`bestProbability == 0`) it picks the first non-mine dead tile — [JS solver_main.js](https://github.com/DavidNHill/JSMinesweeper/blob/c30bd65ba7de859889ea76dccc1d227bed6e51d3/Minesweeper/client/solver_main.js)
- If `offEdgeProbability == 1`, every off-edge tile is cleared. If it is 0 (with full analysis), every off-edge tile is a mine — [JS solver_main.js](https://github.com/DavidNHill/JSMinesweeper/blob/c30bd65ba7de859889ea76dccc1d227bed6e51d3/Minesweeper/client/solver_main.js)
- If the engine found `localClears`, it returns them, passed through `EfficiencyHelper.process()`. But first, unless in no-guess or hardcore mode, it runs `pe.checkForUnavoidable5050OrPseudo()` (`EARLY_FIFTY_FIFTY_CHECKING = true`). If that finds an unresolved 50/50 or pseudo-50/50, the 50/50 guess *replaces* the safe moves — [JS solver_main.js](https://github.com/DavidNHill/JSMinesweeper/blob/c30bd65ba7de859889ea76dccc1d227bed6e51d3/Minesweeper/client/solver_main.js)
- If it found mines but no safe tile, it returns only the mines — [JS solver_main.js](https://github.com/DavidNHill/JSMinesweeper/blob/c30bd65ba7de859889ea76dccc1d227bed6e51d3/Minesweeper/client/solver_main.js)
- **Isolated edge.** If the engine flagged an edge with no covered neighbours outside it (`pe.isolatedEdgeBruteForce`), that edge is brute-forced and solved by `BruteForceAnalysis` on its own ("% chance to solve the isolated edge") — [JS solver_main.js](https://github.com/DavidNHill/JSMinesweeper/blob/c30bd65ba7de859889ea76dccc1d227bed6e51d3/Minesweeper/client/solver_main.js)
- **BFDA.** It runs if `bestProbability < 1` and `finalSolutionsCount < PLAY_BFDA_THRESHOLD`. That threshold is 1000 in play and 5000 for "analyse" (`ANALYSIS_BFDA_THRESHOLD`). Solutions are enumerated only if the iterator's `cycles <= 75,000,000` — [JS BruteForceAnalysis.js `BruteForceGlobal`](https://github.com/DavidNHill/JSMinesweeper/blob/c30bd65ba7de859889ea76dccc1d227bed6e51d3/Minesweeper/client/BruteForceAnalysis.js). This conflicts with the README, which says "750 or less" ([README](https://github.com/DavidNHill/JSMinesweeper/blob/c30bd65ba7de859889ea76dccc1d227bed6e51d3/README.md)). The code value is current.
- **Long-term risk.** `LongTermRiskHelper.findInfluence()` looks for 2-tile and 2x2 pseudo-50/50s and guesses them if found. The order is then `checkForUnavoidable5050OrPseudo()`, then the normal guess — [JS solver_main.js](https://github.com/DavidNHill/JSMinesweeper/blob/c30bd65ba7de859889ea76dccc1d227bed6e51d3/Minesweeper/client/solver_main.js)
- **Normal guess.** It takes `pe.getBestCandidates(0.1, 0.2)` and adds off-edge candidates if `offEdgeProbability > bestOnEdgeProbability * 0.95` (`OFF_EDGE_THRESHOLD`). It runs `tieBreak()` only if the engine took under 50 ms (`pe.duration < 50`); otherwise it plays the safest tile. With no on-edge candidates, `offEdgeGuess()` picks the off-edge tile with the fewest covered neighbours, to hunt zeros and corners — [JS solver_main.js](https://github.com/DavidNHill/JSMinesweeper/blob/c30bd65ba7de859889ea76dccc1d227bed6e51d3/Minesweeper/client/solver_main.js)

**Probability engine data structures (`solver_probability_engine.js`)**
- `BoxWitness` = a revealed number tile, its covered non-mine neighbours (`tiles`) and `minesToFind` (value minus adjacent known mines). Witnesses with an identical tile set are pruned into `prunedWitnesses` for brute force, but all of them are kept for the engine — [JS solver_probability_engine.js constructor / `BoxWitness`](https://github.com/DavidNHill/JSMinesweeper/blob/c30bd65ba7de859889ea76dccc1d227bed6e51d3/Minesweeper/client/solver_probability_engine.js)
- `Box` = an equivalence class of witnessed tiles that are adjacent to exactly the same set of witnesses (`Box.fits(tile, count)`: same witness count and adjacent to all of them). Each box keeps `minMines`/`maxMines`. `maxMines` = min(box size, minesLeft, smallest `minesToFind` of its witnesses). `minMines` = `minesToFind` of any witness whose only box is this one. `emptyTiles` supports "must be empty" constraints (`setMustBeEmpty`) — [JS solver_probability_engine.js `Box`](https://github.com/DavidNHill/JSMinesweeper/blob/c30bd65ba7de859889ea76dccc1d227bed6e51d3/Minesweeper/client/solver_probability_engine.js)
- `ProbabilityLine` = {`mineCount`, `solutionCount` (BigInt), `mineBoxCount[box]` (BigInt: mines in that box summed over all configurations the line represents), `allocatedMines[box]` (int)} — [JS solver_probability_engine.js `extendProbabilityLine`](https://github.com/DavidNHill/JSMinesweeper/blob/c30bd65ba7de859889ea76dccc1d227bed6e51d3/Minesweeper/client/solver_probability_engine.js)
- Constants: `SMALL_COMBINATIONS` (Pascal's triangle to n=8, since a box has at most 8 tiles), `LOW_SAFETY = 1e-8`, so non-certain tiles never round to 0 or 1 — [JS solver_probability_engine.js](https://github.com/DavidNHill/JSMinesweeper/blob/c30bd65ba7de859889ea76dccc1d227bed6e51d3/Minesweeper/client/solver_probability_engine.js)

**Probability engine algorithm (`process`, `mergeProbabilities`, `distributeMissingMines`, `findNextWitness`, `storeProbabilities`, `calculateBoxProbabilities`)**
- It starts from one empty line (solutionCount 1). It takes the first unprocessed witness. For each working line it computes `missingMines = minesToFind − mines already placed in that witness's old (processed) boxes`. Negative: drop the line. Zero: keep it. Otherwise `distributeMissingMines` recursively places `i ∈ [minMines, min(maxMines, missing)]` mines in each *new* box. The last new box takes the exact remainder, and a line is rejected if `mineCount > maxTotalMines`. Each placement multiplies `solutionCount` by `C(boxSize − emptyTiles, k)` — [JS `mergeProbabilities` / `distributeMissingMines` / `extendProbabilityLine`](https://github.com/DavidNHill/JSMinesweeper/blob/c30bd65ba7de859889ea76dccc1d227bed6e51d3/Minesweeper/client/solver_probability_engine.js)
- **Witness order.** `findNextWitness` picks an unprocessed witness adjacent to a processed box. It takes one with 0 unprocessed boxes at once (a pure check), or else the one with the fewest unprocessed boxes. This sweeps along the frontier — [JS `findNextWitness`](https://github.com/DavidNHill/JSMinesweeper/blob/c30bd65ba7de859889ea76dccc1d227bed6e51d3/Minesweeper/client/solver_probability_engine.js)
- **Frontier compression (the key scaling trick).** Once there are ≥100 lines, lines are merged when they have the same `mineCount` and the same `allocatedMines` on every *boundary* box (a box with both processed and unprocessed witnesses). Merging sums `solutionCount` and `mineBoxCount`, using `MergeSorter` and `crunchByMineCount`. Unresolved constraints only depend on boundary boxes, so this is exact. Compressing disables dead-tile analysis for that edge (`canDoDeadTileAnalysis = false`) — [JS `mergeProbabilities` / `MergeSorter` / `crunchByMineCount`](https://github.com/DavidNHill/JSMinesweeper/blob/c30bd65ba7de859889ea76dccc1d227bed6e51d3/Minesweeper/client/solver_probability_engine.js)
- **Independent edges.** When no unprocessed witness touches a processed box, the connected component ("independent edge") is finished. In normal play (not efficiency, analysis or `fullProbability`) it looks for boxes with 0 mines in every working line (`localClears`) or full in every line (`minesFound`). If any local clear exists the engine **stops early** and skips the global calculation. Otherwise it crunches lines by mineCount only. `storeProbabilities()` then convolves them with `heldProbs` (the earlier components): the cartesian product of lines, mineCount added (kept only if ≤ maxTotalMines), solutionCount multiplied, and `mineBoxCount = a.mbc·b.sol + b.mbc·a.sol`. The result is collapsed to one line per total mine count — [JS `findNextWitness` / `storeProbabilities`](https://github.com/DavidNHill/JSMinesweeper/blob/c30bd65ba7de859889ea76dccc1d227bed6e51d3/Minesweeper/client/solver_probability_engine.js)
- **Global mine count (binomial weighting)** in `calculateBoxProbabilities`. For each held line with `mineCount ≥ minTotalMines` (where `minTotalMines = minesLeft − TilesOffEdge`): `mult = C(minesLeft − mineCount, TilesOffEdge)`, `totalTally += mult·solutionCount`, `box.mineTally += mult·mineBoxCount[box] / boxSize`, `outsideTally += mult·(minesLeft − mineCount)·solutionCount`. Box safety = `1 − mineTally/totalTally`, and off-edge safety = `1 − outsideTally/(totalTally·TilesOffEdge)`. `finalSolutionsCount = totalTally` is the exact number of full-board solutions — [JS `calculateBoxProbabilities`](https://github.com/DavidNHill/JSMinesweeper/blob/c30bd65ba7de859889ea76dccc1d227bed6e51d3/Minesweeper/client/solver_probability_engine.js)
- Binomials come from `binomialCache = new BinomialCache(5000, 1000, BINOMIAL)`. The engine refuses to run (`validWeb = false`) if `TilesOffEdge > binomialCache.getMaxN()` — [JS main.js](https://github.com/DavidNHill/JSMinesweeper/blob/c30bd65ba7de859889ea76dccc1d227bed6e51d3/Minesweeper/client/main.js); [JS solver_probability_engine.js constructor](https://github.com/DavidNHill/JSMinesweeper/blob/c30bd65ba7de859889ea76dccc1d227bed6e51d3/Minesweeper/client/solver_probability_engine.js)
- Outputs: `bestLivingSafety` and second-best (both initialised to off-edge safety, counting only non-dead tiles), `singleSafestTile` (set if strictly safest), `blendedSafety = (4·best + second)/5`, `bestOnEdgeProbability`, `bestProbability = max(onEdge, offEdge)`, `emptyBoxes`, `localClears`, `livingClearTile` (count of safe, non-dead tiles) — [JS `calculateBoxProbabilities`](https://github.com/DavidNHill/JSMinesweeper/blob/c30bd65ba7de859889ea76dccc1d227bed6e51d3/Minesweeper/client/solver_probability_engine.js)
- README: "The calculation is 100% accurate, but this comes at the price of exponential processing cost based on the number of revealed tiles which can be strung together … 50x50/500 should be fine, 100x100/2500 might struggle" — [README](https://github.com/DavidNHill/JSMinesweeper/blob/c30bd65ba7de859889ea76dccc1d227bed6e51d3/README.md)

**Dead tiles (`getCandidateDeadLocations`, `checkCandidateDeadLocations`)**
- README definition: dead tiles are "either mines or have only one possible value … it is never correct to choose a dead tile unless all the tiles left in the game are dead" — [README](https://github.com/DavidNHill/JSMinesweeper/blob/c30bd65ba7de859889ea76dccc1d227bed6e51d3/README.md)
- A candidate is any witnessed tile whose covered neighbours are all in boxes. Its adjacent boxes are split into `goodBoxes`, which lie entirely within the tile's neighbourhood (or are the tile itself), and `badBoxes`. A tile with no adjacent boxes is a "lonely tile" and is dead unless it is certainly a mine — [JS `getCandidateDeadLocations`](https://github.com/DavidNHill/JSMinesweeper/blob/c30bd65ba7de859889ea76dccc1d227bed6e51d3/Minesweeper/client/solver_probability_engine.js)
- After each independent edge, a candidate stays dead only if, in every working line where its own box is not entirely mines, (a) each bad box is either empty or completely full (for its own box, full minus the candidate) and (b) the total mines in good boxes is the same. Then the number it would reveal is fixed. If any of its boxes fell outside the edge, or the edge was compressed, it is marked alive (conservative). On a single complete edge with no off-edge tiles, only lines with `mineCount == minesLeft` count — [JS `checkCandidateDeadLocations`](https://github.com/DavidNHill/JSMinesweeper/blob/c30bd65ba7de859889ea76dccc1d227bed6e51d3/Minesweeper/client/solver_probability_engine.js)
- Dead tiles are dropped from candidate lists (`getBestCandidates`) unless safe, and sorted last in `compare()`. The secondary-safety pass also marks a tile dead when only one of its values is consistent (`validValues == 1`) — [JS solver_main.js `compare` / `secondarySafetyAnalysis`](https://github.com/DavidNHill/JSMinesweeper/blob/c30bd65ba7de859889ea76dccc1d227bed6e51d3/Minesweeper/client/solver_main.js)

**50/50 and pseudo-50/50 detection**
- `checkForUnavoidable5050()`: for each pruned witness with `0 < minesToFind < |tiles|` and |tiles| > 1, if every covered non-mine tile next to any of its tiles (outside the set) is adjacent to *all* of its tiles, nothing can ever tell them apart, so it is an unavoidable guess. Witnesses with exactly 1 mine and 2 tiles become `Link`s, which record "breaker" tiles and whether each end is closed. Links are chained through shared tiles. A chain closed at both ends with an even number of extensions and no breaker outside the area (`noBreaker`) is an extended 50/50 — [JS `checkForUnavoidable5050`](https://github.com/DavidNHill/JSMinesweeper/blob/c30bd65ba7de859889ea76dccc1d227bed6e51d3/Minesweeper/client/solver_probability_engine.js)
- README: the solver finds "arbitrarily extended 2-tile 50/50s", "enclosed 2x2/2 boxes", "2-tile pseudo-50/50s" and "4-tile 2x2 pseudo-50/50s". It "is unable to discover extended pseudo-50/50s". "Since the 50/50 will never change it is always correct to guess these at the earliest opportunity" — [README](https://github.com/DavidNHill/JSMinesweeper/blob/c30bd65ba7de859889ea76dccc1d227bed6e51d3/README.md)
- `LongTermRiskHelper` (`INFLUENCE_THRESHOLD = 0.025`). For every horizontal and vertical pair of hidden tiles (`getHorizontal`/`getVertical`) and every 2x2 (`getBoxInfluence`), it collects the hidden "closing" tiles beyond the pattern that would need to be mines. For a horizontal pair these are the 3 tiles left and 3 tiles right. It skips patterns needing more than `maxMissingMines` (2 for pairs) or more than `minesLeft`. It temporarily marks closers + tile1 as mines and tile2 as safe, then counts solutions (`solver.countSolutions` → `SolutionCounter`). That count is the "influence tally". **If the influence tally equals the tile's `mineTally`** (every solution where the tile is a mine is one where it sits in an unresolvable 50/50), the tile is a **pseudo-50/50** and is guessed now. Influences above 2.5% are stored per tile, and "enablers" (the closers) also get influence. `findTileInfluence` caps influence at min(mineTally, total − mineTally) — [JS LongTermRiskHelper.js](https://github.com/DavidNHill/JSMinesweeper/blob/c30bd65ba7de859889ea76dccc1d227bed6e51d3/Minesweeper/client/LongTermRiskHelper.js)
- `FiftyFiftyHelper` is the "old method" with fixed patterns, and its call is commented out in `doSolve` — [JS solver_main.js](https://github.com/DavidNHill/JSMinesweeper/blob/c30bd65ba7de859889ea76dccc1d227bed6e51d3/Minesweeper/client/solver_main.js)
- Toggles: `SolverGlobal.EARLY_FIFTY_FIFTY_CHECKING = true` (check even when safe tiles exist), `CALCULATE_LONG_TERM_SAFETY = true`, `PRUNE_GUESSES = true`, `REUSE_BRUTE_FORCE_ANALYSIS = false` — [JS solver_main.js `SolverGlobal`](https://github.com/DavidNHill/JSMinesweeper/blob/c30bd65ba7de859889ea76dccc1d227bed6e51d3/Minesweeper/client/solver_main.js)

**Guess selection (`getBestCandidates`, `getOffEdgeCandidates`, `tieBreak`, `secondarySafetyAnalysis`, `compare`, `findAlternativeMove`)**
- **Candidates.** Boxes are taken in descending safety while `safety ≥ bestLivingSafety − 0.1`, or while fewer than 2 candidates and `safety ≥ bestLivingSafety − 0.2`. This is subtractive (`SELECTION_THRESHOLD1 = 0.1`, `SELECTION_THRESHOLD2 = 0.2`), and dead tiles are excluded — [JS `getBestCandidates`](https://github.com/DavidNHill/JSMinesweeper/blob/c30bd65ba7de859889ea76dccc1d227bed6e51d3/Minesweeper/client/solver_probability_engine.js). The README instead says multiplicative "within 10% … 80% * 90% = 72%" ([README](https://github.com/DavidNHill/JSMinesweeper/blob/c30bd65ba7de859889ea76dccc1d227bed6e51d3/README.md)), so the code and docs disagree.
- **Off-edge candidates** (only if off-edge safety > 0.95 × best on-edge). If fewer than 30 tiles are off the edge, all of them. Otherwise the off-edge tiles at the 4 orthogonal distance-2 offsets from each witness (all 16 ring-2 offsets on high-density boards), plus off-edge tiles with 2–3 covered neighbours — [JS `getOffEdgeCandidates`](https://github.com/DavidNHill/JSMinesweeper/blob/c30bd65ba7de859889ea76dccc1d227bed6e51d3/Minesweeper/client/solver_main.js)
- `tieBreak` adds tiles with 50/50 influence and safety above `best − 0.1` (`ltr.getInfluencedTiles`), then scores each candidate with `secondarySafetyAnalysis` — [JS `tieBreak`](https://github.com/DavidNHill/JSMinesweeper/blob/c30bd65ba7de859889ea76dccc1d227bed6e51d3/Minesweeper/client/solver_main.js)
- **`secondarySafetyAnalysis(pe, board, action, best, ltr)`**, step by step — [JS solver_main.js](https://github.com/DavidNHill/JSMinesweeper/blob/c30bd65ba7de859889ea76dccc1d227bed6e51d3/Minesweeper/client/solver_main.js):
  1. Rerun the engine with the tile forced empty (`runProbabilityEngine(board,[tile])`). If that makes some *other multi-tile* box 100% safe that wasn't before, the tile is **dominated**: `weight = p·(1 + p·0.001)`, progress = p, and the function returns. Each newly safe single-tile box that isn't dead adds to `linkedTilesCount`.
  2. `fiftyFiftyInfluence = 1 + 0.9 · ltr.findTileInfluence(tile) / safetyTally`, where safetyTally = number of solutions in which the tile is safe.
  3. For each possible value v from adjFlags to adjFlags + adjCovered: reveal v, rerun the full engine (forced to completion with `playStyle = EFFICIENCY`), then set P(v) = solutions_v / total and add `blendedSafety += P(v) · work.blendedSafety · influence` and `secondarySafety += P(v) · work.bestLivingSafety`. The outcome counts as "progress" if `livingClearTile > linkedTilesCount`. It also tracks expected clears, the tiles safe for every value (`commonClears`), and whether the same `singleSafestTile` comes up after every value.
  4. **Pruning bound** before each value: `(blendedSafety + probLeft · influence)·(1 + (progress + probLeft)·0.001) < best.weight` stops the evaluation.
  5. Final `weight = blendedSafety · (1 + progress · 0.001)`. With only one valid value the tile is dead. If the same strictly safer tile is always safest next, `dominatingTile` is set to it.
- In the current code `progressContribution = 0.001` ("tiny amount to favour progress if everything else is the same"). The old `PROGRESS_CONTRIBUTION = 0.2` survives only in the unused `fullAnalysis()`. So the README's "progress … blended" is now in effect a tie-break, and the main metric is two-step safety — [JS solver_main.js](https://github.com/DavidNHill/JSMinesweeper/blob/c30bd65ba7de859889ea76dccc1d227bed6e51d3/Minesweeper/client/solver_main.js); the Java solver has the same, with `PROGRESS_CONTRIBUTION = 0.001` and `0.052` commented out — [JAVA SolverSettings.java](https://github.com/DavidNHill/Minesweeper/blob/827e5b9b898ec9b8a8b03383b42a374ad12586b1/MineSweeperSolver/src/minesweeper/solver/settings/SolverSettings.java)
- **`compare`**: flags last, dead tiles last, higher `weight` first, then higher `expectedClears`. After sorting: (a) a partial BFDA may swap in a better move (`bfda.checkForBetterMove`); (b) `findAlternativeMove`: if a candidate more than 0.001 safer is among the best move's `commonClears` (best safe ⇒ alternative safe), swap them; (c) a `dominatingTile` replaces the best move — [JS `tieBreak` / `compare` / `findAlternativeMove`](https://github.com/DavidNHill/JSMinesweeper/blob/c30bd65ba7de859889ea76dccc1d227bed6e51d3/Minesweeper/client/solver_main.js)
- README: "to win a classic expert game of minesweeper the solver is required, on average, to make 3.3 guesses" and "the guessing heuristic may not be optimal for high density boards" — [README](https://github.com/DavidNHill/JSMinesweeper/blob/c30bd65ba7de859889ea76dccc1d227bed6e51d3/README.md)
- `USE_HIGH_DENSITY_STRATEGY = false`. It would sort by safety, then minimum `maxSolutions` ("solution space reduction"). The comment reads: "I think 'secondary safety' generally works better" — [JS solver_main.js](https://github.com/DavidNHill/JSMinesweeper/blob/c30bd65ba7de859889ea76dccc1d227bed6e51d3/Minesweeper/client/solver_main.js)

**Brute force (`Brute_force.js`: `WitnessWebIterator`, `Cruncher`)**
- `pe.generateIndependentWitnesses()` greedily picks pairwise non-overlapping witnesses. The iterator holds one `SequentialIterator` "cog" per independent witness, choosing `minesToFind` of its tiles, plus a final cog placing the remaining mines over every other covered tile. `cycles` = product of the binomials. The `Cruncher` keeps a sample only if every dependent witness is satisfied — [JS Brute_force.js](https://github.com/DavidNHill/JSMinesweeper/blob/c30bd65ba7de859889ea76dccc1d227bed6e51d3/Minesweeper/client/Brute_force.js)
- Each stored solution is an array over all covered tiles: `BOMB`, or the number that tile would show (adjacent known mines + adjacent mines in the sample) — [JS `Cruncher.checkSample`](https://github.com/DavidNHill/JSMinesweeper/blob/c30bd65ba7de859889ea76dccc1d227bed6e51d3/Minesweeper/client/Brute_force.js)

### Inferences
- In Rust, the engine maps naturally to: `Box { tiles: SmallVec<[u16;8]>, witnesses, min, max }` and a `Line { mines: u16, count: BigUint/u128/f64, box_mines: Vec<Big>, alloc: Vec<u8> }`. Merging is a hash map keyed on `(mines, alloc[boundary boxes])`. Convolution across components is an array indexed by mine count. Exact counts for 30x16/99 can exceed u128 (C(381,99) is about 10^93), so use big integers or log-domain f64 with per-mine-count ratios.
- The early stop on `localClears` means probabilities are often not computed when a safe move exists. A bot can do the same: play safe tiles, recompute.
- The move-selection "score" is close to E[P(survive this guess) × blended P(survive the best next guess)], scaled up for tiles that may resolve a 50/50. Ties are broken by progress, then expected clears, plus dominance checks.

### Gaps
- `checkForUnavoidable5050OrPseudo()` (lines 407–774) and the 2x2 branch of `LongTermRiskHelper` were skimmed, not traced line by line. The pseudo-chain rules beyond what is described above are not documented here.
- `EfficiencyHelper` (chording and flag economy) was not analysed. It changes click count, not win rate, in the default no-flag style.

## Q2. Other strong open-source solvers: how do they differ?

### Takeaway
Hill's Java solver is the original of JSMinesweeper and adds a "local search" stage, larger configurable brute-force budgets and an "adversarial rollout" mode. minesweepr computes exact per-cell probabilities by grid-agnostic rule reduction, permutation cross-elimination and front enumeration, but plays only the lowest-probability cell at random. Other popular solvers (Python, C++) use CSP enumeration plus heuristic or one-step look-ahead scoring and report about 38–39% on expert.

### Cited Findings

**Hill Java solver (`DavidNHill/Minesweeper`)**
- README stages: 1) trivial search; 2) **local search** ("considers each revealed tile and tries every way of placing the remaining mines around it"); 3) probability engine ("exact (to 20 decimal places)"); 4) brute force; 5) brute force deep analysis "when the number of candidate solutions is less then 4000" — [JAVA README](https://github.com/DavidNHill/Minesweeper/blob/827e5b9b898ec9b8a8b03383b42a374ad12586b1/README.md)
- Move methods in `Solver.java`: `TRIVIAL`, `LOCAL`, `UNAVOIDABLE_GUESS`, `GUESS`, `ROLLOUT`, `PROBABILITY_ENGINE`, `BOOK` (the configured opening move) — [JAVA Solver.java](https://github.com/DavidNHill/Minesweeper/blob/827e5b9b898ec9b8a8b03383b42a374ad12586b1/MineSweeperSolver/src/minesweeper/solver/Solver.java)
- **Adversarial rollout.** "if we have few enough solutions do an adversarial rollout": when no move is found, no certain clear exists, the best guess is not off-edge and the solution count is under `rolloutSolutions` (default 0, i.e. off), a `RolloutGenerator` builds random boards and `adversarial(bestCandidates)` picks the move. - JS README: the Java solver is stronger and "The Javascript version is slightly weaker" (JS is slower, so it has smaller budgets) — [JSMinesweeper README](https://github.com/DavidNHill/JSMinesweeper/blob/c30bd65ba7de859889ea76dccc1d227bed6e51d3/README.md)

**minesweepr (mrgris)**
- The solver is geometry-agnostic. Its input is `Rule(num_mines, cells)` plus `MineCount(total_cells, total_mines)` (or a fixed mine probability) — [MSR README](https://github.com/mrgriscom/minesweepr/blob/b9d9989ad8b2955c4c2a44690b34f88fc02ed4d5/README.md)
- `solve()` pipeline: `condense_supercells` (cells with identical rule membership become one "supercell", which is the same idea as Hill's box) → `reduce_rules` (subset subtraction: a super-rule minus a sub-rule, choosing reductions by `metric` = bigger rules first, then mine counts nearest the extremes) → remove trivial rules → `permute_and_interfere` (list each rule's permutations, then `cross_eliminate` removes those with no compatible permutation in an overlapping rule, cascading, and `rereduce` splits rules whose permutation sets factor as cartesian products) → `split_fronts` (connected components) → `enumerate_front` (a `FrontTally` per front, with sub-tallies per mine count holding the configuration count and expected mines per cell) → `cell_probabilities` — [MSR minesweeper.py `solve`, `Reduceable.metric`, `PermutedRuleset.cross_eliminate`/`rereduce`](https://github.com/mrgriscom/minesweepr/blob/b9d9989ad8b2955c4c2a44690b34f88fc02ed4d5/minesweeper.py)
- **Global mine count**: `combine_fronts` folds the fronts (plus an "uncharted cells" pseudo-front with weights `discrete_relative_likelihood(n, k, k0) = C(n,k)/C(n,k0)`) into a `CombinedFront`, pruning partial sums that can't reach `at_large_mines`. It then rescales each front's per-mine-count sub-tallies. The fixed-density variant uses `(p/(1−p))^(k−k0)` — [MSR `combine_fronts`, `discrete_relative_likelihood`, `nondiscrete_relative_likelihood`](https://github.com/mrgriscom/minesweepr/blob/b9d9989ad8b2955c4c2a44690b34f88fc02ed4d5/minesweeper.py)
- It raises `InconsistencyError` on contradictions, including mine-count consistency (`check_count_consistency`) — [MSR minesweeper.py](https://github.com/mrgriscom/minesweepr/blob/b9d9989ad8b2955c4c2a44690b34f88fc02ed4d5/minesweeper.py)
- **Guess policy is naive.** `Solution.process` collects the cells with minimum mine probability (within EPSILON) as `best_guesses`, and auto-play picks one at random (`choose_rand`). The first move is a random cell — [MSR web_demo player.js](https://github.com/mrgriscom/minesweepr/blob/b9d9989ad8b2955c4c2a44690b34f88fc02ed4d5/web_demo/minesweepr/static/script/player.js)
- The web service has a CPU quota (`settings.CPU_QUOTA`) because "solving minesweeper is inherently an exponential algorithm" — [MSR README](https://github.com/mrgriscom/minesweepr/blob/b9d9989ad8b2955c4c2a44690b34f88fc02ed4d5/README.md)
- The demo supports first-click modes "safe" and "opening" (`ensure_safety(pos, first_safe == 'opening')`) — [MSR minesweeper.js](https://github.com/mrgriscom/minesweepr/blob/b9d9989ad8b2955c4c2a44690b34f88fc02ed4d5/web_demo/minesweepr/static/script/minesweeper.js)

**gamescomputersplay/minesweeper-solver (Python)**
- Methods in order, with their share of moves: Naive 88%, Groups (subset) 8%, Subgroups ("no more than"/"at least") 1.4%, Coverage (global count) 0.2%, CSP per cluster 0.2%, whole-board brute force 0.02%, Probability 1.7%. - Reports "38.6±0.3% for a standard Expert game (30x16, 99 mines)" with "First click is always on an all-zero coordinate cell" — [gamescomputersplay README](https://github.com/gamescomputersplay/minesweeper-solver)

**ArolaunTech/minesweeperbot (C++)**
- Stages: trivial, then full enumeration of mine combinations and a click on the safest cell, then a brute-force perfect-move search when there are under 100,000 configurations ("adds about 0.7% to the Expert win rate"). It reports 91.40% ± 0.17% beginner, 77.29% ± 0.26% intermediate and 39.33% ± 0.30% expert over 100,000 trials each. ### Inferences
- The proven strong recipe is the same everywhere: exact probability by component enumeration with global mine-count weighting, then a look-ahead that rewards information and next-move safety, then exact search in small endgames. Hill's solver adds dead-tile and 50/50 handling, which a naive "lowest probability" policy like minesweepr's lacks.
- ArolaunTech's numbers suggest the endgame search alone is worth well under 1 percentage point on expert. Most of Hill's lead over plain safest-cell solvers probably comes from secondary safety and 50/50 handling, though the rules differ between solvers, so the comparison is not exact.

**minesweepr author's write-up (mrgris.com project page, fetched with curl)**
- It computes cell safety "by counting how many configurations in which it appears empty, as a proportion of all possible configurations, assuming all configurations are equally likely". It splits the board into independent groups: "what would have taken a×b×c amount of work takes a+b+c instead" — [mrgris.com Minesweepr](https://mrgris.com/projects/minesweepr/)
- The author says the algorithm "only computes the safest cell(s) for the very next move" and does no look-ahead ("this algorithm doesn't concern itself with that"). He deliberately leaves out edge/corner "folk wisdom" — [mrgris.com Minesweepr](https://mrgris.com/projects/minesweepr/)

**Tu, Li, Chen, Zu, Gu, "Exploring Efficient Strategies for Minesweeper" (AAAI-17 Workshop WS-17-15, pp. 999–1005), PDF read in full via curl**

## Q3. Exact enumeration vs approximation: component splitting, mine-count weighting with large interiors, cost limits and fallbacks

### Takeaway
Neither Hill's solver nor minesweepr approximates. Both split the frontier into connected components, enumerate each exactly (Hill with frontier-state merging), and combine components by mine count. The unconstrained interior is handled in closed form, as one aggregate block weighted by `C(interior, minesLeft − frontierMines)`, so a large interior costs nothing. Cost limits apply only to the frontier (no limit in Hill's engine, a CPU timeout in minesweepr) and to brute force and BFDA, which have hard thresholds and fall back to the heuristic guess.

### Cited Findings
- Hill: a component is found when `findNextWitness` cannot find an unprocessed witness touching a processed box ("we have processed a complete set of independent witnesses"). Components are kept per mine count and convolved in `storeProbabilities` — [JS solver_probability_engine.js](https://github.com/DavidNHill/JSMinesweeper/blob/c30bd65ba7de859889ea76dccc1d227bed6e51d3/Minesweeper/client/solver_probability_engine.js)
- Hill: the interior is never enumerated. `TilesOffEdge = squaresLeft − witnessed.length`. `mult = combination(minesLeft − pl.mineCount, TilesOffEdge)` multiplies each total-mine-count line, and one off-edge probability is shared by all interior tiles — [JS `calculateBoxProbabilities`](https://github.com/DavidNHill/JSMinesweeper/blob/c30bd65ba7de859889ea76dccc1d227bed6e51d3/Minesweeper/client/solver_probability_engine.js)
- Hill: exactness comes from BigInt arithmetic, and probabilities are converted with `divideBigInt(…, 8)` (8 decimal places). The engine is disabled only if the interior exceeds the binomial cache (n=5000) or mine counts are invalid — [JS solver_probability_engine.js constructor](https://github.com/DavidNHill/JSMinesweeper/blob/c30bd65ba7de859889ea76dccc1d227bed6e51d3/Minesweeper/client/solver_probability_engine.js)
- Hill: the cost of an edge is bounded by the number of distinct `(mineCount, allocatedMines on boundary boxes)` states. Compression starts at ≥100 lines (`if (newProbs.length < 100 && this.canDoDeadTileAnalysis) return newProbs`) — [JS `mergeProbabilities`](https://github.com/DavidNHill/JSMinesweeper/blob/c30bd65ba7de859889ea76dccc1d227bed6e51d3/Minesweeper/client/solver_probability_engine.js)
- Hill: the guess look-ahead reruns the engine up to 9 times per candidate, so `tieBreak` is skipped when one engine run took ≥50 ms (`if (pe.duration < 50)`) — [JS solver_main.js](https://github.com/DavidNHill/JSMinesweeper/blob/c30bd65ba7de859889ea76dccc1d227bed6e51d3/Minesweeper/client/solver_main.js)
- Hill: brute force is gated by `finalSolutionsCount < 1000` (play) or `< 5000` (analysis) and `iterator.cycles <= 75,000,000`. BFDA stops after `BRUTE_FORCE_ANALYSIS_MAX_NODES = 100,000,000`, and an incomplete BFDA is kept only as `partialBFDA` for `checkForBetterMove` — [JS BruteForceAnalysis.js](https://github.com/DavidNHill/JSMinesweeper/blob/c30bd65ba7de859889ea76dccc1d227bed6e51d3/Minesweeper/client/BruteForceAnalysis.js); [JS solver_main.js](https://github.com/DavidNHill/JSMinesweeper/blob/c30bd65ba7de859889ea76dccc1d227bed6e51d3/Minesweeper/client/solver_main.js)
- minesweepr: the interior is an `UnchartedCell` meta-front whose mine-count weights are `C(n,k)/C(n,k0)` (as floats via `fact_div`). Fronts are combined with min/max pruning, and runaway cases are handled only by a process timeout (`CPU_QUOTA`) — [MSR minesweeper.py `combine_fronts`](https://github.com/mrgriscom/minesweepr/blob/b9d9989ad8b2955c4c2a44690b34f88fc02ed4d5/minesweeper.py); [MSR README](https://github.com/mrgriscom/minesweepr/blob/b9d9989ad8b2955c4c2a44690b34f88fc02ed4d5/README.md)
- minesweepr reduces the frontier logically *before* enumerating (subset reduction, permutation cross-elimination, cartesian decomposition through `rereduce`), which can split one front into several independent ones — [MSR minesweeper.py `PermutedRuleset.rereduce`](https://github.com/mrgriscom/minesweepr/blob/b9d9989ad8b2955c4c2a44690b34f88fc02ed4d5/minesweeper.py)
- gamescomputersplay brute-forces each cluster's CSP, and runs whole-board brute force only "when few cells and mines remain" — [gamescomputersplay README](https://github.com/gamescomputersplay/minesweeper-solver)

### Inferences
- On 30x16/99 the frontier rarely has more than a few dozen boxes, and Hill's frontier-DP keeps state counts small, so exact computation runs in milliseconds in compiled code. A Rust port has no need for sampling.
- For Rust numerics, a simple exact option is `num-bigint`. Alternatively, keep per-component counts as u128/f64, combine with weights normalised against a reference mine count (minesweepr's ratio trick: `C(n,k)/C(n,k0)` as an f64 product), and use exact integers only to test for "== 0" and "== total". Hill decides certainty with exact comparisons (`mineTally == 0`, `== totalTally`), not epsilons.

### Gaps
- Neither author publishes worst-case timing on expert boards. Only Hill's qualitative "50x50/500 fine, 100x100/2500 might struggle" is available.

## Q4. How are endgames solved exactly (game-tree search)?

### Takeaway
Hill's BFDA enumerates every remaining solution, each as a vector of per-tile outcomes (mine or revealed number). It then searches the game tree by recursion: a move splits the solution set by the value revealed, a node's worth is the number of solutions in which perfect play wins, and a node with no informative tile left scores 1. The search uses alpha-style pruning, a transposition table, merging of tiles that carry identical information, and the rule that a safe move is always played first.

### Cited Findings
- Input: `allSolutions` (each an array over tiles of `BOMB` or a value 0–8), wrapped in a `SolutionTable` that stores a random hash per solution. Each `Node` owns a contiguous range `[startLocation, endLocation)` of the solution table, which is re-sorted in place by the probed tile's value (`sortSolutions`) — [JS BruteForceAnalysis.js `SolutionTable`, `LivingLocation.buildChildNodes`](https://github.com/DavidNHill/JSMinesweeper/blob/c30bd65ba7de859889ea76dccc1d227bed6e51d3/Minesweeper/client/BruteForceAnalysis.js)
- **Living location** = a tile with more than one distinct non-mine value across the node's solutions (`count > 1` in `determineLivingLocations`). It records `mineCount`, `zeroSolutions`, `maxSolutions`, `min/maxValue`, and `linkedHash` = Σ hash(solution) where safe − Σ hash(solution) where mine. A tile whose `linkedHash` matches an earlier one splits the solutions identically, so it is marked `linked` and `pruned` (skipped) — [JS `Node.determineLivingLocations`](https://github.com/DavidNHill/JSMinesweeper/blob/c30bd65ba7de859889ea76dccc1d227bed6e51d3/Minesweeper/client/BruteForceAnalysis.js)
- **Move ordering** (`LivingLocation.compareTo`): fewer `mineCount` first (safest), unlinked first, more `zeroSolutions`, more distinct values, smaller `maxSolutions` — [JS BruteForceAnalysis.js](https://github.com/DavidNHill/JSMinesweeper/blob/c30bd65ba7de859889ea76dccc1d227bed6e51d3/Minesweeper/client/BruteForceAnalysis.js)
- **Recursion** (`Node.getWinningLines(depth, move, cutoff)`): `notMines = size − move.mineCount`. If `result + notMines <= cutoff`, prune, because the move cannot beat the current best. Otherwise it builds children by value. A child with no living locations has `winningLines = 1`. Otherwise it iterates the child's living moves in order: it breaks when `size − mineCount ≤ child.winningLines`, keeps the max (ties go to the move with higher `mineCount`), and **breaks after the first move with `mineCount == 0`**, since a certainly safe move needs no comparison. Children with more than 10 solutions are cached in a `TranspositionTable` (32 "mega buckets") keyed by the `Position` hash. After each child, if `result + remaining notMines ≤ cutoff` it prunes — [JS `Node.getWinningLines`, `getWinningLinesStart`](https://github.com/DavidNHill/JSMinesweeper/blob/c30bd65ba7de859889ea76dccc1d227bed6e51d3/Minesweeper/client/BruteForceAnalysis.js)
- Top level (`process`): every living location of the root is evaluated. Win chance = `best / allSolutions.size()`. `completed` is set only if `processCount < BRUTE_FORCE_ANALYSIS_MAX_NODES`. The tree is kept to `BRUTE_FORCE_ANALYSIS_TREE_DEPTH = 6` for reuse, but reuse is off (`REUSE_BRUTE_FORCE_ANALYSIS = false`). If every tile is dead, the move is the first non-mine tile — [JS BruteForceAnalysis.js `process`](https://github.com/DavidNHill/JSMinesweeper/blob/c30bd65ba7de859889ea76dccc1d227bed6e51d3/Minesweeper/client/BruteForceAnalysis.js); [JS solver_main.js](https://github.com/DavidNHill/JSMinesweeper/blob/c30bd65ba7de859889ea76dccc1d227bed6e51d3/Minesweeper/client/solver_main.js)
- README: BFDA "(conceptionally) plays every combination of move against every combination of mines and determines the best way to play to maximise the chance of winning … finds a perfect path". The Java README's example picks a 66.67%-safe tile (win 46.23%) over 75%-safe tiles (best win 44.64%), with "1008 solutions … explored 67984 nodes … 253 milliseconds" — [JSMinesweeper README](https://github.com/DavidNHill/JSMinesweeper/blob/c30bd65ba7de859889ea76dccc1d227bed6e51d3/README.md); [JAVA README](https://github.com/DavidNHill/Minesweeper/blob/827e5b9b898ec9b8a8b03383b42a374ad12586b1/README.md)
- The same BFDA solves an isolated edge independently of the rest of the board (`checkEdgeIsIsolated` → `isolatedEdgeBruteForce`) — [JS solver_probability_engine.js `checkEdgeIsIsolated`](https://github.com/DavidNHill/JSMinesweeper/blob/c30bd65ba7de859889ea76dccc1d227bed6e51d3/Minesweeper/client/solver_probability_engine.js)
- ArolaunTech: a perfect-move search below 100,000 configurations, worth about +0.7% on expert — [ArolaunTech README](https://github.com/ArolaunTech/minesweeperbot)

### Inferences
- The BFDA does not model flood-fill cascades. After a 0 is revealed its neighbours become living tiles with `mineCount == 0`, which are played first by the "safe move ⇒ break" rule. For win probability this is equivalent, because safe probes only add information. A Rust port can keep this simplification and use one probe per node.
- Because the uniform solution set is the posterior, BFDA is correct only if every remaining solution is equally likely. That holds for uniform placement conditioned on the visible board. It does not hold exactly under XP-style first-click relocation (see Q5).
- In Rust: `solutions: Vec<[u8; N]>` (N = number of covered tiles, 255 = mine), in-place partitioning per node (as `sortSolutions` does), `u64` Zobrist-style hashes of the (tile, value) history, and an `FxHashMap<u64, u32>` transposition table.

### Gaps
- The exact semantics of "winningLines = 1" when the remaining solutions cannot be told apart (the forced final guesses) are taken from the code, not from a write-up. In effect it assumes you win exactly one of k indistinguishable solutions.
- The Java `BruteForceAnalysisParallel` and the in-progress (2026-08) hashing changes were not read.

## Q5. Reported win rates and the first-click rules behind them

### Takeaway
On expert, the best first-party figures are Hill's Java solver: about 40–41% with a safe (not necessarily opening) first click in a corner, and about 53–54.3% with a guaranteed opening at (3,3). Tu et al.'s PSEQ gets 39.6% (40.06% with exact endgame search) under the same safe-first-click, corner-start rule, and pure safest-cell play gets about 33–35.6% (minesweepr 33.1%). Other open-source solvers report 38.6–39.3% under different or unstated rules. Runesweeper (safe first click by mine relocation, no guaranteed opening) is in the "classic" ~40% regime. Its XP-style relocation of the first-click mine to the top-left also makes the posterior slightly non-uniform.

### Inferences
- With XP relocation, conditioning on the first click being safe is not uniform. Boards where the clicked cell held a mine now have an extra mine at the first free top-left cell, so top-left cells (excluding the last row and column) carry slightly more mine probability than a uniform model assigns. A Runesweeper solver that wants exact probabilities should either (a) treat the original layout as uniform and mix two hypotheses, "first click was safe originally" and "a mine was moved to the first free cell in row-major order", or (b) accept a tiny bias. The effect is largest early, on cells near the top-left.
- To compare against Hill's 40–41%, a Runesweeper benchmark should use expert 30x16/99 with a safe-not-opening first click and a corner start, and report that rule with every number.

### Gaps
- No first-party statement gives the number of games behind Hill's 41% / 54.3%.
- Win rates for beginner and intermediate under the classic rule were not found in Hill's READMEs.
- Buffet's ~38.7% and Legendre's ~37.5% are as quoted by Tu et al., not read from the original papers.
- Ranking under the classic expert rule (safe first click, no guaranteed opening), different sample sizes: Hill Java 40–41% (corner start) > Tu PSEQ-D\* 40.06% > PSEQ 39.62% > safest-cell solvers 33–35.6% (minesweepr 33.1%; Tu "P" with corner start 35.56%). ArolaunTech's 39.33% and gamescomputersplay's 38.6% (opening first click) are not directly comparable.
