## Simon Tatham's Mines: generator loop, solver, perturbation, first click, retries

### Takeaway
Tatham's Mines is the oldest and most widely cited guess-free generator. It does not use rejection sampling. It uses **solver-guided perturbation**. It places mines uniformly, then runs a set-based solver (single-clue rules plus pairwise subset/"wing" deductions, with a capped global mine-count step). Whenever the solver stalls, it calls `mineperturb()`. That function swaps mines between a randomly chosen stuck constraint set and nearby squares, so the set becomes all-mine or all-clear while the total mine count stays fixed. The solver is then re-run from scratch until a run needs zero perturbations. If progress stalls, the generator restarts with a fresh random layout. From try 101 onward it allows "big" perturbations over the whole unknown region. The first click is always a guaranteed opening (its 3×3 neighbourhood is mine-free).

### Cited Findings
**Where the code lives and what it promises**
- The manual promises: "it will generate its mine positions in such a way as to ensure that you never need to *guess* where a mine is". "Ensure solubility" is on by default, and turning it off gives "the riskier grids generated by other implementations" — [puzzles.but L1128-1134, L1211-1216](https://github.com/samfundev/puzzles/blob/ede745aa858b1a47e3b12803879716ef173ed7a7/puzzles.but#L1128-L1216)
- In the current code, `default_params()` has `unique = true`. The presets include 9×9/10, 16×16/40, **30×16/99 (20.6%)** and **30×16/170 (35.4%)**, as well as hex, triangular, Penrose, hat and Spectre grids — [mines.c L925-962](https://github.com/samfundev/puzzles/blob/ede745aa858b1a47e3b12803879716ef173ed7a7/mines.c#L925-L962)
- Commit `d324fe9` (2026-09-02, "Mines: support play on a wide range of grid shapes") generalised the solver from 3×3-bitmask sets to arbitrary neighbour lists. For square grids, the leftover sets are re-sorted into the old order so that "the present code generates the same game" as older versions — [commit d324fe9](https://github.com/samfundev/puzzles/commit/d324fe9c4733e3d48b0d28d5f5daf63c5db5c48b); [mines.c L2471-2518](https://github.com/samfundev/puzzles/blob/ede745aa858b1a47e3b12803879716ef173ed7a7/mines.c#L2471-L2518). The old representation was `struct set { short x, y, mask, mines; ... }` — [old mines.c L303-307](https://github.com/ghewgill/puzzles/blob/01c3e382d9c7013f0bb4eb9f1ff2d19bb05d4241/mines.c#L303-L307)

**Solver: `minesolve()`, L1956-2665**
- **Inputs and outputs.** The board array holds -1 (known mine), 0..N (opened number) and -2 (unknown). The return value is -1 for "stalled", 0 for "solved with no perturbation", and >0 for "solved after k perturb calls" — [mines.c L1937-1952](https://github.com/samfundev/puzzles/blob/ede745aa858b1a47e3b12803879716ef173ed7a7/mines.c#L1937-L1952)
- **Building sets.** Each opened number becomes a set: its unknown neighbours plus a remaining mine count (the clue minus known neighbouring mines). When a square becomes known, it is removed from every set that contains it, and duplicate or empty sets are dropped — [mines.c L1994-2079](https://github.com/samfondev/puzzles/blob/ede745aa858b1a47e3b12803879716ef173ed7a7/mines.c#L1994-L2079)
- **Deduction 1, trivial rule.** If `mines == 0` or `mines == n`, every square in the set is clear or every square is a mine — [L2095-2113](https://github.com/samfundev/puzzles/blob/ede745aa858b1a47e3b12803879716ef173ed7a7/mines.c#L2095-L2113)
- **Deduction 2, pairwise "wings".** For each overlapping set s2, the code computes s−s2 and s2−s. If one set has extra mines equal to the size of its wing, that wing is all mines and the other wing is all clear — [L2128-2153](https://github.com/samfundev/puzzles/blob/ede745aa858b1a47e3b12803879716ef173ed7a7/mines.c#L2128-L2153)
- **Deduction 3, subset splitting.** If s ⊂ s2, the code adds a new set s2−s with `mines = s2.mines − s.mines`, and likewise the other way round. Derived sets can feed later deductions — [L2155-2172](https://github.com/samfundev/puzzles/blob/ede745aa858b1a47e3b12803879716ef173ed7a7/mines.c#L2155-L2172)
- **Deduction 4, global mine count.** This step runs only when the local to-do list is empty, and only if the total n is known (n ≥ 0; with n < 0 it is skipped):
  - First, if minesleft == 0 or minesleft == squaresleft, everything left is decided.
  - Otherwise the code enumerates **maximal disjoint unions of the current sets**. If the squares outside a union must be all mines or all clear, they are marked. This is capped "at n=10 to avoid too much pain": `bool setused[10]` and `if (nsets <= lenof(setused))`. With more than 10 sets in the store, the enumeration is skipped entirely.
  - Source: [L2183-2432](https://github.com/samfundev/puzzles/blob/ede745aa858b1a47e3b12803879716ef173ed7a7/mines.c#L2183-L2432)
- **When it counts as stuck.** If a full pass does nothing (`done_something` is false), the solver "really [is] at our wits' end". It picks a **uniformly random remaining set** (`random_upto(rs, ss->n)`) and calls `perturb(ctx, board, s)`. If no sets remain, it calls `perturb(ctx, board, NULL)`, meaning "the entire unknown set".
- **After a perturbation.** For each returned change, the mine count of every set containing that tile is adjusted and the set is put back on the to-do list. Squares that had been opened as clear are re-queued.
- **When perturb returns NULL**, the solver gives up. Any remaining -2 square makes the return value -1.
- Source for the last three points: [L2520-2648](https://github.com/samfundev/puzzles/blob/ede745aa858b1a47e3b12803879716ef173ed7a7/mines.c#L2520-L2648)
- **What the solver does not do.** There is no full CSP or backtracking search, no exact enumeration of frontier components, and no probability reasoning. Reasoning is pairwise set algebra plus a capped disjoint-union global count. This is my reading of the whole of `minesolve()`, [L1956-2665](https://github.com/samfundev/puzzles/blob/ede745aa858b1a47e3b12803879716ef173ed7a7/mines.c#L1956-L2665)

**Perturbation: `mineperturb()`, L2744-3146**
- **Candidate squares.** The function excludes the start tile and its neighbours, and the squares of the set being perturbed. The rest are sorted by class, with a random tiebreak:
  - class 1: unknown squares bordering known space
  - class 2: unknown squares beyond that boundary
  - class 3 ("as a very last resort"): already-known squares
  - Source: [L2795-2859](https://github.com/samfundev/puzzles/blob/ede745aa858b1a47e3b12803879716ef173ed7a7/mines.c#L2795-L2859)
- **Choosing the swap.** The code counts `nfull` and `nempty` in the set. It walks the candidate list until it has found either `nfull` empty squares (so the set can be **emptied**: its mines move out) or `nempty` mined squares (so the set can be **filled**: mines move in), whichever comes first. The total mine count is conserved — [L2905-2928, L2994-3064](https://github.com/samfundev/puzzles/blob/ede745aa858b1a47e3b12803879716ef173ed7a7/mines.c#L2905-L3064)
- **Partial fill.** If neither is possible, the set is always partly *filled* with random squares. The comment's reason: at very high densities "the only way to get a solvable board is going to be to pack most of the mines solidly around the edges" — [L2935-2991](https://github.com/samfundev/puzzles/blob/ede745aa858b1a47e3b12803879716ef173ed7a7/mines.c#L2935-L2991)
- **Updating the board.** Numbers already shown on the board are updated in place. A known square can flip state: one that becomes a mine is marked -1, and one that becomes clear gets its number recomputed. So the generator can "un-solve" squares it had already solved — [L3069-3119](https://github.com/samfundev/puzzles/blob/ede745aa858b1a47e3b12803879716ef173ed7a7/mines.c#L3069-L3119)
- **Big perturbations.** With `s == NULL`, the whole unknown region is the set. These are allowed only when `allow_big_perturbs`. The author's comment: this "appears to make it guaranteeably possible to generate a workable board for any mine density, but they tend to be a bit boring, with mines packed densely into far corners … Therefore … I disable this feature for the first few attempts" — [L2728-2760](https://github.com/samfundev/puzzles/blob/ede745aa858b1a47e3b12803879716ef173ed7a7/mines.c#L2728-L2760)
- **Progress guard.** `nperturbs_since_last_new_open` is reset whenever a square that had *never* been opened is opened (`mineopen()`, L2681-2702). `mineperturb` returns NULL once the counter reaches w or h, i.e. min(w,h) — [L2762-2769](https://github.com/samfundev/puzzles/blob/ede745aa858b1a47e3b12803879716ef173ed7a7/mines.c#L2762-L2769)
  - The guard was added in `a7c7826` (2025-07-29) to fix a reproducible infinite loop (`mines --generate 1 9x15n55X1Y1#2-94`). The loop was a cleared region ringed with mines, which the perturber repeatedly filled and re-cleared. Tatham: "I'm not at all happy with this fix … what I _ought_ to do is rethink the entire strategy of perturbation, in the large-scale case" — [commit a7c7826](https://github.com/samfundev/puzzles/commit/a7c7826bce5cbb9b9c337c11b9b7f8b278e76fba)
  - `fc9c4ab` (2026-08-31) fixed a double increment of that counter. The fix changed generated boards for the same seed — [commit fc9c4ab](https://github.com/samfundev/puzzles/commit/fc9c4abecaccc2adc8768ca818b0722511a548a6)
- **Apparent bug (my reading, not tested).** The partial-fill branch for a local set reuses `i` as both the loop counter and the output index: `for (i = 0; i < s->n; i++) { … if (!ctx->mines[tile]) setlist[i++] = tile; }` — [L2953-2959](https://github.com/samfundev/puzzles/blob/ede745aa858b1a47e3b12803879716ef173ed7a7/mines.c#L2953-L2959). This line was introduced by the grid-generalisation commit `d324fe9` (`git log -S`). The old code collected the list with separate dx/dy loops — [old mines.c ~L1540-1556](https://github.com/ghewgill/puzzles/blob/01c3e382d9c7013f0bb4eb9f1ff2d19bb05d4241/mines.c#L1540-L1556). As written, the new loop skips set members and leaves `setlist` entries uninitialised, so it could pick garbage tiles. It only fires in the high-density partial-fill path. **Unverified by execution.**

**Generator loop: `minegen()`, L3148-3290**
- **Each try.** Place n mines uniformly at random among squares that are neither the start tile nor its neighbours, capped at the number of eligible squares.
- **Inner loop.**
  - Reset the knowledge board, open the start tile, and `assert(solvegrid[tile] == 0)`, which holds "by deliberate arrangement".
  - Run `minesolve(... mineopen, mineperturb ...)`.
  - Stop with success when it returns 0, i.e. a fresh solve of the *now-modified* layout needs no perturbation.
  - Abort this try if it returns -1, or if the perturbation count did not decrease from the previous run (`solveret >= prevret`).
- **Outer loop.** `do { … } while (!success)` has no cap on tries. `allow_big_perturbs = (ntries > 100)`.
- Source: [L3148-3290](https://github.com/samfundev/puzzles/blob/ede745aa858b1a47e3b12803879716ef173ed7a7/mines.c#L3148-L3290). The old version had the same `ntries > 100` rule — [old mines.c L1813](https://github.com/ghewgill/puzzles/blob/01c3e382d9c7013f0bb4eb9f1ff2d19bb05d4241/mines.c#L1813)
- **Global count.** The solver *is* given the true mine count n (`minesolve(gi, w, h, n, …)`, L3268-3269), so it may use global-count deductions, within the 10-set cap.
- **First click.** In interactive play the layout is generated lazily inside `open_square()` on the first click, with that tile as the start (L3676-3690). So the first click is always a zero, i.e. a guaranteed opening. Batch generation (`--generate`) picks a random start tile and still consumes the same RNG, so seed plus click is reproducible — [L3403-3506](https://github.com/samfundev/puzzles/blob/ede745aa858b1a47e3b12803879716ef173ed7a7/mines.c#L3403-L3506); [L3676-3690](https://github.com/samfundev/puzzles/blob/ede745aa858b1a47e3b12803879716ef173ed7a7/mines.c#L3676-L3690)
- **Edge cases.**
  - The old code rejected `n > w*h − 9` and grids with w or h ≤ 2 when unique was on. The comment explains that thin strips can be impossible: for example, an odd mine count in a 2-row strip "you are doomed" — [old mines.c L248-268](https://github.com/ghewgill/puzzles/blob/01c3e382d9c7013f0bb4eb9f1ff2d19bb05d4241/mines.c#L248-L268)
  - Since `7c79620`, too many mines is no longer a validation error. Unplaced mines are recorded as `+nnn` in the game description — [commit 7c79620](https://github.com/samfundev/puzzles/commit/7c796205a5a714e8ae43fefe4b1c993a979b935f)
- **Timing hook.** A `TIME_MINELAYOUT` compile flag prints "Mine layout time" — [L3359-3371](https://github.com/samfundev/puzzles/blob/ede745aa858b1a47e3b12803879716ef173ed7a7/mines.c#L3359-L3371). Tatham's `benchmark.sh` runs every preset with `--time-generation --generate 100` — [benchmark.sh](https://github.com/samfundev/puzzles/blob/ede745aa858b1a47e3b12803879716ef173ed7a7/benchmark.sh)

### Inferences
- **Completeness.** Because of the perturbation loop, Tatham's generator effectively never fails at standard densities, even at 35% (a shipped preset). There is no rejection-rate problem, but the cost is a non-uniform distribution (see the distribution section).
- **Solver strength.** It is weaker than a perfect logician: no exact component enumeration, and the global count is capped at ≤10 sets. Every Tatham board is therefore solvable by a fairly human-like rule set (single-clue, pairwise subset/wing, simple global count). A complete solver would also solve it, but the set of boards it can emit is narrower than "all boards a perfect logician can solve".
- **What "success" means.** It is "a fresh solve from the start needs 0 perturbations". The final layout is verified by the same solver that shaped it.
- **Speed.** Each solver pass is roughly linear in board size. Most of the time should go on restarts and repeated re-solves. That it is fast at Expert is plausible, but **I did not measure it**.

## Other generators: minesweeper.online, JSMinesweeper, mindsweeper, Kaboom, other open source; rejection vs constructive vs perturbation

### Takeaway
Implementations fall into three groups:
1. **Rejection sampling, i.e. generate-and-test.** Examples: mindsweeper (Rust), Anonymine, and, by snippet only, minesweeper.online.
2. **Solver-guided perturbation or repair.** Examples: Tatham, lrvideckis Android, quasarbright, sam-gc, and JSMinesweeper's hybrid (local "balancing" repair plus reseed when it fails).
3. **Lazy or adversarial placement with no board up front.** Example: Kaboom, which uses SAT.

I found no truly constructive generator that builds a board clue by clue.

### Cited Findings
**JSMinesweeper (David Hill)**
- **Generator loop.** `createNoGuessGame()` loops `while (!won && loopCheck < maxLoops)`, with `maxLoops = 1000000` solver calls. Each iteration:
  - Builds a new seeded `ServerGame` with start style `"zero"`, which excludes the first click and all its neighbours from mines, i.e. a guaranteed opening.
  - Plays it with the solver in `noGuessingMode`.
  - If the solver returns `fillers`, applies them with `game.fix(filler)`.
  - If the solver's best action has `prob != 1`, logs "Made a guess", abandons the seed and draws a new random seed.
  - Source: [MinesweeperGame.js L366-500](https://github.com/DavidNHill/JSMinesweeper/blob/c30bd65ba7de859889ea76dccc1d227bed6e51d3/Minesweeper/client/MinesweeperGame.js#L366-L500); zero-start exclusion at [L622-633](https://github.com/DavidNHill/JSMinesweeper/blob/c30bd65ba7de859889ea76dccc1d227bed6e51d3/Minesweeper/client/MinesweeperGame.js#L622-L633)
- **Repair step.** When the probability engine finds no certain move (`pe.bestProbability < 1 && options.noGuessingMode`), `findBalancingCorrections(pe)` looks for witnesses that can be made trivially solvable:
  - Remove all of a witness's remaining mines, or fill all of its free squares.
  - Compensate with one or two **non-overlapping** witnesses whose add/remove counts balance exactly, so the total mine count is preserved.
  - If no balance is found, `fillerTiles` is cleared and the run falls through to a guess, which triggers a reseed.
  - Source: [solver_main.js L614-631, L1938-2148](https://github.com/DavidNHill/JSMinesweeper/blob/c30bd65ba7de859889ea76dccc1d227bed6e51d3/Minesweeper/client/solver_main.js#L1938-L2148)
- `game.fix()` adds or removes a mine and updates adjacent numbers — [MinesweeperGame.js L955-995](https://github.com/DavidNHill/JSMinesweeper/blob/c30bd65ba7de859889ea76dccc1d227bed6e51d3/Minesweeper/client/MinesweeperGame.js#L955-L995)
- **Solver strength.** The probability engine "calculates the chance that a tile is a mine for every hidden tile … The calculation is 100% accurate", at exponential cost in connected revealed tiles — [README](https://github.com/DavidNHill/JSMinesweeper/blob/c30bd65ba7de859889ea76dccc1d227bed6e51d3/README.md). The README describes the No Guess option as: "Attempts to generate a board which contains no guesses. The board is generated on your first click." — [README](https://github.com/DavidNHill/JSMinesweeper/blob/c30bd65ba7de859889ea76dccc1d227bed6e51d3/README.md)

**mindsweeper (Alex Buz, Rust/WASM)**
- **Pure rejection sampling.** In `LocalGame::new`, a `loop { … }`:
  - Shuffles `mine_count` mines into the non-protected squares (first click plus neighbours are protected).
  - Reveals the first click.
  - Repeatedly reveals all squares `analyzer.find_safe_moves(false)` returns.
  - Returns the untouched pre-click layout as soon as the game is won. If no safe move exists, it loops and reshuffles.
  - Source: [src/server/local.rs L335-401](https://github.com/AlexBuz/mindsweeper/blob/b804faa439cf0c210289e7045f3cb7152fa386d1/src/server/local.rs#L335-L401)
- **Analyzer strength.** It is exact:
  - It partitions the frontier into components.
  - It enumerates every component's possible mine arrangements by mine count.
  - It combines components with the *global* remaining mine count and the unconstrained "floating" squares, setting `unconstrained_implies_safe` / `unconstrained_implies_mine`.
  - A square is deduced only if no globally consistent assignment disagrees.
  - Source: [src/analyzer.rs L295-445](https://github.com/AlexBuz/mindsweeper/blob/b804faa439cf0c210289e7045f3cb7152fa386d1/src/analyzer.rs#L295-L445)
- **Mindless mode** returns only trivially known-safe tiles, so the generator then accepts only boards solvable by trivial rules — [analyzer.rs L380-390](https://github.com/AlexBuz/mindsweeper/blob/b804faa439cf0c210289e7045f3cb7152fa386d1/src/analyzer.rs#L380-L390)
- **Claims (author's, not verified by me).** "Uniform sampling … If a particular mine arrangement is solvable by a perfect logician without guessing, then it's just as likely to be picked by the algorithm as every other viable arrangement." It "accomplishes this within a matter of milliseconds after you make your first click" — [README](https://github.com/AlexBuz/mindsweeper/blob/b804faa439cf0c210289e7045f3cb7152fa386d1/README.md). The Expert preset is 30×16/99 and "Evil" is 30×20/130 — [src/server/mod.rs L119-131](https://github.com/AlexBuz/mindsweeper/blob/b804faa439cf0c210289e7045f3cb7152fa386d1/src/server/mod.rs#L119-L131)
- **Guess punishment.** `rearrange_mines()` resamples the hidden layout uniformly among all arrangements consistent with what is visible. It weights solution groups by exact `BigUint` combination counts, then picks a uniform arrangement per component and uniform floating mines — [local.rs L131-194](https://github.com/AlexBuz/mindsweeper/blob/b804faa439cf0c210289e7045f3cb7152fa386d1/src/server/local.rs#L131-L194)

**Kaboom (Paweł Marczewski)**
- **No board is fixed in advance.** Each click asks a SAT solver (bundled `minisat.js`) whether the clicked cell *can* be safe or *can* be a mine, given all revealed labels and a cardinality counter for the global mine count (`assertCounterAtLeast/AtMost`).
- **Adversarial rule.** The game picks a safe shape only if the cell cannot be dangerous, or if no provably safe cell exists anywhere (`!hasSafeCells`). Otherwise it picks a shape in which the cell is a mine. Guessing when a safe deduction exists is therefore always punished, and forced guesses are always survived.
- Source: [index.js L137-192 (reveal), L570-670 (Solver)](https://github.com/pwmarcz/kaboom/blob/2c5cc170ae7a2ac6faf4da348e13b50c5c3dddb4/index.js#L137-L670)

**lrvideckis Minesweeper_Android**
- **Repair loop.** `getSolvableBoard()` runs:
  - Local rules, then Gaussian elimination, then a bounded backtracking solver (`IntenseRecursiveSolver`, which throws `HitIterationLimitException`).
  - When stuck, it either "randomly move[s] the positions of non-deducible 'interesting' mines, and move[s] 1 'interesting' mine to a square not next to any clue" (`shuffleInterestingMinesAndMakeOneAway`, every 12th iteration), or backtracks a stack of earlier states and calls `shuffleAwayMines()`.
  - It does a full restart on failure and gives up only on an interrupt or timeout.
  - Source: [CreateSolvableBoard.java](https://github.com/lrvideckis/Minesweeper_Android/blob/7881613ab995e80da0f9e43e0898bede853b4754/app/src/main/java/com/LukeVideckis/minesweeper_android/minesweeperStuff/minesweeperHelpers/CreateSolvableBoard.java)

**Anonymine (Oskar Skog)**
- **Rejection sampling.** "If the field can't be solved, a new will be randomized". `init_field2()` forks several worker processes that test random fields in parallel, with `maxtime` per field. The start point and its neighbours are never mines.
- Source: [FAQ](https://github.com/oskar-skog/anonymine/blob/b8fc3e418e48403a7d1636cd808c6b33abd3f093/FAQ); [anonymine_engine.py L650-760](https://github.com/oskar-skog/anonymine/blob/b8fc3e418e48403a7d1636cd808c6b33abd3f093/anonymine_engine.py#L650-L760)

**quasarbright/minesweeper (2024)**
- **Repair loop.** `generateGuessFree()` makes up to 100 attempts. Each one solves with "count sets" (hand-written rules, "with a SAT solver as backup"). If stuck, it moves one random frontier mine to a random non-mine square beyond the frontier. If no frontier mine exists, it starts over.
- The author's own TODO notes this causes "a concentration of mines on the outside".
- Source: [src/model/solver.ts L261-302](https://github.com/quasarbright/minesweeper/blob/fbf155788fd85f4ef50207c57ad63a86b2caba8b/src/model/solver.ts#L261-L302); [solver.md](https://github.com/quasarbright/minesweeper/blob/fbf155788fd85f4ef50207c57ad63a86b2caba8b/solver.md)

**sam-gc/minesweeper-generator-solver (2014, C)**
- **Repair loop.** `gen_no_guess_board()` loops `while(!solve_board(board))`, calling `adjust_random_board()`. It regenerates from scratch when the adjust count repeats three times, and `exit(0)`s after `GEN_MAX` iterations.
- Source: [solver.c L274-322](https://github.com/sam-gc/minesweeper-generator-solver/blob/560fd9d808b5adbbcb93dceb3e55a451dd0b4ad0/solver.c#L274-L322)

**minesweeper.online and other web clones (snippets only, unverified)**
- minesweeper.online was unreachable. That retry behaviour is consistent with rejection sampling — [1000mines.com (snippet)](https://www.1000mines.com/)
- minesweeper.now describes: generate around the protected first click, run its deduction solver, reject if a guess is needed — [minesweeper.now FAQ (snippet)](https://minesweeper.now/faq/no-guessing-minesweeper)
- **mrgriscom/minesweepr** is an exact probability solver with "guaranteed opening" first clicks, not a no-guess generator. ### Inferences
- **"Most established."** Tatham's perturbation generator is the longest-lived and best-known guess-free implementation. It has been in a widely packaged collection for about 20 years and has active upstream maintenance through 2026. The current state of the art for *distributional quality*, however, is rejection sampling with an exact solver (mindsweeper), and JSMinesweeper's hybrid is in between.
- **Perturbation vs rejection.**
  - Perturbation (Tatham, lrvideckis, quasarbright, sam-gc) trades distribution bias for guaranteed termination at high density.
  - Rejection (mindsweeper, Anonymine) is unbiased relative to its solver, but its cost grows as 1/acceptance-rate, which collapses above the density phase transition (see Academic).
  - JSMinesweeper repairs locally while conserving mine count, and reseeds when repair fails.

## What "solvable without guessing" means in each implementation

### Takeaway
"No-guess" is always relative to a specific solver. The definitions differ in two ways: the deduction strength, and whether the global mine count may be used.

### Cited Findings
- **Tatham Mines.**
  - Deductions: single-set trivial rule, pairwise wing/subset deductions with derived sets, and a global mine-count step. The global step is used only when local rules stall, and only when there are ≤10 sets.
  - No exhaustive CSP.
  - The first click is a forced zero.
  - Source: [mines.c L2085-2432](https://github.com/samfundev/puzzles/blob/ede745aa858b1a47e3b12803879716ef173ed7a7/mines.c#L2085-L2432)
- **JSMinesweeper.**
  - Deductions: an exact probability engine, which is full CSP over the frontier including the mine count. A move counts as no-guess only if its probability is exactly 1.
  - The generator plays with `advancedGuessing = false` and `PLAY_STYLE_NOFLAGS`.
  - Source: [MinesweeperGame.js L379-384](https://github.com/DavidNHill/JSMinesweeper/blob/c30bd65ba7de859889ea76dccc1d227bed6e51d3/Minesweeper/client/MinesweeperGame.js#L379-L384); [README](https://github.com/DavidNHill/JSMinesweeper/blob/c30bd65ba7de859889ea76dccc1d227bed6e51d3/README.md)
- **mindsweeper.**
  - Normal mode: a "perfect logician", meaning exact component enumeration plus global mine count including floating cells. Mindless mode: trivial rules only.
  - Source: [analyzer.rs L371-445](https://github.com/AlexBuz/mindsweeper/blob/b804faa439cf0c210289e7045f3cb7152fa386d1/src/analyzer.rs#L371-L445)
- **Kaboom.** Exact deduction via SAT with min/max mine-count cardinality constraints. The game also *forbids* guessing whenever a safe deduction exists — [index.js L614-670](https://github.com/pwmarcz/kaboom/blob/2c5cc170ae7a2ac6faf4da348e13b50c5c3dddb4/index.js#L614-L670)
- **lrvideckis.** Local rules, Gaussian elimination, then backtracking with an iteration cap. If the cap is hit, a deducible move may be missed and the board gets repaired anyway — [CreateSolvableBoard.java](https://github.com/lrvideckis/Minesweeper_Android/blob/7881613ab995e80da0f9e43e0898bede853b4754/app/src/main/java/com/LukeVideckis/minesweeper_android/minesweeperStuff/minesweeperHelpers/CreateSolvableBoard.java)
- **quasarbright.** Count-set rules with a SAT backup — [solver.md](https://github.com/quasarbright/minesweeper/blob/fbf155788fd85f4ef50207c57ad63a86b2caba8b/solver.md)
- **Commercial sites.** Third-party guides note that minesweeper.online's no-guessing mode guarantees completability, not easiness, and may need complex reasoning — [puzzlesarcade.com (snippet)](https://www.puzzlesarcade.com/behind-the-games/why-minesweeper-sometimes-forces-a-guess-the-math-behind-a-5050); [mossmoss.net (snippet)](https://mossmoss.net/guides/minesweeper-no-guess/)

### Inferences
- A board accepted by a weaker solver (Tatham, Mindless) is always acceptable to a stronger one, but not the other way round. Stronger solvers therefore accept more boards, which raises the rejection-sampling acceptance rate and lowers bias, at the cost of harder logic for players.
- With the global mine count allowed, endgame "count-the-mines" positions are legal no-guess positions. Without it, those boards need extra repair or rejection.
- Every implementation surveyed protects the first click's 3×3 neighbourhood, making the first click a guaranteed opening.

### Gaps
- Unknown whether minesweeper.online's solver uses the global mine count, or what its deduction depth is.

## Board distribution: bias, artifacts, effect on 3BV and difficulty

### Takeaway
Rejection sampling with solver S gives the *exact uniform* distribution over boards that S can solve from the click. Perturbation and repair generators do not. By their authors' own admission they push mines away from the solved region, toward far edges and corners. That lowers interior density and makes boards easier, and in the worst case leaves dense mine blocks in corners.

### Cited Findings
- **Tatham on big perturbations.** They produce boards "a bit boring, with mines packed densely into far corners of the board and the remainder being less dense than one might like". Partial fills deliberately "pack most of the mines solidly around the edges" at high density — [mines.c L2736-2742, L2938-2946](https://github.com/samfundev/puzzles/blob/ede745aa858b1a47e3b12803879716ef173ed7a7/mines.c#L2728-L2946)
- **Tatham's preference order.** Mines are moved preferentially to frontier unknown squares (class 1), then far unknown squares (class 2), then already-solved squares (class 3). The 3×3 around the start is never touched — [mines.c L2795-2859](https://github.com/samfundev/puzzles/blob/ede745aa858b1a47e3b12803879716ef173ed7a7/mines.c#L2795-L2859)
- **lrvideckis on its own generator.** The cons are that "many mines will be eventually moved to the outside of the board effectively making the board smaller" and that "the mine density of the inside of the board will be smaller, which generally creates easier boards" — [CreateSolvableBoard.java](https://github.com/lrvideckis/Minesweeper_Android/blob/7881613ab995e80da0f9e43e0898bede853b4754/app/src/main/java/com/LukeVideckis/minesweeper_android/minesweeperStuff/minesweeperHelpers/CreateSolvableBoard.java)
- **quasarbright's TODO.** "randomly decide between moving a mine out of the frontier vs moving a mine INTO the frontier — this will avoid a concentration of mines on the outside" — [solver.ts L271-274](https://github.com/quasarbright/minesweeper/blob/fbf155788fd85f4ef50207c57ad63a86b2caba8b/src/model/solver.ts#L271-L274)
- **mindsweeper's claim** of uniform sampling over perfect-logician-solvable boards — [README](https://github.com/AlexBuz/mindsweeper/blob/b804faa439cf0c210289e7045f3cb7152fa386d1/README.md). This follows from its code: a uniform shuffle in a reject-until-accept loop, [local.rs L335-401](https://github.com/AlexBuz/mindsweeper/blob/b804faa439cf0c210289e7045f3cb7152fa386d1/src/server/local.rs#L335-L401)
- **Acceptance rate (unsourced).** A third-party explainer estimates that only "~5–15%" of random Expert boards are no-guess solvable. It gives no source and no solver definition, so treat it as unverified — [minesweeperblast.com (snippet)](https://minesweeperblast.com/minesweeper-board-generation/)
- **Related figure.** JSMinesweeper's Java solver wins 41% of classic Expert games (safe start in a corner) and 54.3% of modern Expert games (opening at (3,3)) when it is allowed to guess optimally — [JSMinesweeper README](https://github.com/DavidNHill/JSMinesweeper/blob/c30bd65ba7de859889ea76dccc1d227bed6e51d3/README.md)

### Inferences
- **Artifacts of perturbation generators:**
  - Fewer 50/50 structures by construction. Every stuck set is made all-mine or all-clear.
  - Inhomogeneous density: low near the start, high at the edges and corners.
  - "Walls" of mines along edges at high density.
  - A solved interior that is easier than a uniform no-guess board of the same nominal density.
- **3BV.** Lower interior density usually means larger openings and fewer isolated numbers, so lower 3BV is likely for perturbation boards. This is inference only; I found no measured 3BV comparison.
- **Rejection with an exact solver** is unbiased among no-guess boards. That conditional distribution still differs from unconditional uniform: by definition it excludes 50/50 shapes and probably favours larger openings. That is a property of "no-guess", not a generator artifact.
- **JSMinesweeper's balancing repair** keeps the mine count exactly and makes only small, local, non-overlapping edits. Its bias is plausibly smaller than Tatham's class-ordered swaps, but it is not uniform.

### Gaps
- No quantitative comparisons (density maps, 3BV histograms, 50/50 counts) across generators were found or measured. The sandbox blocked running code.
- The 5–15% Expert acceptance rate is unsourced. I found no primary measurement of no-guess acceptance at 30×16/99 with an opening.

## Academic work on uniquely solvable / no-guess boards and uniform sampling

### Takeaway
The academic literature covers the *complexity* of Minesweeper consistency and inference, and a density *phase transition* in logical solvability. I found no peer-reviewed paper on generating no-guess boards or sampling them uniformly. The practical knowledge lives in open-source code.

### Cited Findings
- **Kaye (2000)** showed the Minesweeper consistency problem is NP-complete. This is via secondary summaries — [minesweeperblast.com (snippet)](https://minesweeperblast.com/no-guess-minesweeper/); [Demaine & Hearn survey, arXiv cs/0106019](https://arxiv.org/pdf/cs/0106019)
- **Scott, Stege & van Rooij**, "Minesweeper May Not Be NP-Complete but Is Hard Nonetheless", Mathematical Intelligencer 33 (2011), argue the inference question is coNP-complete — [Springer PDF mirror](https://hn.jakechampion.name/reader/https://link.springer.com/content/pdf/10.1007/s00283-011-9256-x.pdf); [MaRDI record](https://portal.mardi4nfdi.de/wiki/Publication:660171)
- **MIT Hardness Group (FUN 2024)** reports a flaw in the published coNP-hardness proofs for inference and supplies a corrected proof — [arXiv 2404.14519 (snippet)](https://arxiv.com/abs/2404.14519); [LIPIcs FUN 2024 paper 25](https://drops.dagstuhl.de/storage/00lipics/lipics-vol291-fun2024/LIPIcs.FUN.2024.25/LIPIcs.FUN.2024.25.pdf)
- **Dempsey & Guinn**, "A Phase Transition in Minesweeper" (FUN 2020, arXiv 2008.04116), find empirically a SAT-like phase transition: "above the critical mine density it becomes almost impossible to play Minesweeper by logical inference", with algorithmic barriers at the transition. This is via search snippet; the full text was unreachable — [arXiv 2008.04116](https://arxiv.org/pdf/2008.04116)
- "Algorithms for Minesweeper Game Grid Generation" (2017) is listed on minesweepergame.com, but **its contents could not be retrieved** (host blocked) — [PDF link](https://minesweepergame.com/math/algorithms-for-minesweeper-game-grid-generation-2017.pdf)

### Inferences
- Exact deduction is coNP-hard in general. Practical exact solvers (JSMinesweeper, mindsweeper) are exponential only in the size of connected frontier components, which stay small at standard densities.
- The phase transition explains why rejection sampling is cheap at Beginner/Intermediate and still workable at Expert (about 20.6%), but collapses at very high density (Tatham's 35% preset). There, only perturbation-style generators reliably terminate.
- **Uniform sampling.** Exact uniform sampling over no-guess boards is easy by rejection when acceptance is not tiny. I know of no MCMC or exact-counting method for no-guess boards in the literature.

### Gaps
- I could not read the full texts of Dempsey & Guinn, Kaye, or the 2017 grid-generation paper (hosts blocked), so critical density values are not quoted.
- No paper on uniform sampling of no-guess boards was found.

## Recommendation for a Rust desktop/web clone needing instant Expert generation

### Takeaway
Use **rejection sampling with a layered exact solver**, as in mindsweeper:
- Generate on the first click, with the 3×3 around the click protected.
- Solve with trivial and subset rules first, then fall back to exact frontier-component enumeration with the global mine count, using exact (big-integer or log-space) combination counts.
- Accept the first board fully solved from the click.

This gives exact uniformity over "perfect-logician" no-guess boards. It is simple to implement and verify, and the one shipped Rust/WASM implementation reports millisecond times at Expert. Keep a Tatham-style perturbation fallback, or a capped attempt budget, only for very high custom densities.

### Cited Findings
- mindsweeper is a working Rust/WASM proof of concept. It does pure rejection, uses an exact analyzer with global count, has an Expert preset, and claims ms-level generation ("generally finishes running before you even release the mouse button") — [README](https://github.com/AlexBuz/mindsweeper/blob/b804faa439cf0c210289e7045f3cb7152fa386d1/README.md); [local.rs L335-401](https://github.com/AlexBuz/mindsweeper/blob/b804faa439cf0c210289e7045f3cb7152fa386d1/src/server/local.rs#L335-L401)
- Tatham's perturbation guarantees termination at high density but introduces corner and edge packing. The author also called the 2025 stall fix provisional ("not at all happy") — [mines.c L2728-2742](https://github.com/samfundev/puzzles/blob/ede745aa858b1a47e3b12803879716ef173ed7a7/mines.c#L2728-L2742); [commit a7c7826](https://github.com/samfundev/puzzles/commit/a7c7826bce5cbb9b9c337c11b9b7f8b278e76fba)
- JSMinesweeper shows a middle path: count-preserving local balancing plus reseeding — [solver_main.js L1938-2148](https://github.com/DavidNHill/JSMinesweeper/blob/c30bd65ba7de859889ea76dccc1d227bed6e51d3/Minesweeper/client/solver_main.js#L1938-L2148)
- runesweeper's current `Game::lay_mines` follows Windows XP's `rand() % n` placement. Its first click on a mine moves that mine to the first free square, row by row. A no-guess mode would need a separate first-click generation path — [src/game.rs L124-186](/home/user/runesweeper/src/game.rs)

### Inferences
- **Why rejection over perturbation for this project:**
  - (a) Uniform and principled. "No-guess" then means exactly "every board the chosen solver can finish is equally likely", which is easy to document and test.
  - (b) No artifacts like edge packing or lower interior density.
  - (c) Simple failure mode: you just draw again.
  - (d) Rust speed makes many attempts per frame budget feasible.
  - (e) A seed plus first-click index reproduces the board, matching Tatham's seed/click harmonisation (mines.c L3446-3456).
- **Engineering suggestions** (inferred, not measured):
  - Solve incrementally: only re-run exact enumeration when the trivial and subset rules stall.
  - Cap component enumeration, and treat hitting the cap as rejection, so worst-case time stays bounded.
  - Run attempts in parallel on desktop (rayon). Note that mindsweeper's comment says `find_map_first` "doesn't seem to speed this up at all" ([local.rs L336](https://github.com/AlexBuz/mindsweeper/blob/b804faa439cf0c210289e7045f3cb7152fa386d1/src/server/local.rs#L336)).
  - On the web, spread attempts across frames or a Web Worker.
  - Expose solver strength as a design decision: with or without global count, trivial-only "easy NG" vs full logic.
  - For custom densities above about 25–30%, fall back after N attempts to JSMinesweeper-style balancing or Tatham-style perturbation, and tell the user the board is "repaired".
- **Benchmark before committing.** Measure acceptance rate and p99 latency at 30×16/99 with a 3×3 opening. This research produced no measured numbers.

### Gaps
- No measured generation latency, acceptance rate or worst case for any generator at Expert. Execution was blocked, and the published numbers found are vendor claims or unsourced.
- mindsweeper's "milliseconds" claim is unverified.
